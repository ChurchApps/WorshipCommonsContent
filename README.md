# WorshipCommons Content Library

The source-of-truth content for [worshipcommons.org](https://worshipcommons.org) —
an open library of worship music. Everything here is freely usable: see
[LICENSE.md](LICENSE.md) for the per-section terms.

## Layout

```
songs/<lang>/<license>/<slug>-<id>/   one package per song, e.g. songs/en/public-domain/amazing-grace-YxPfAFYWOaG/
  sources/                            original bytes; never edited
  masters/                            human-approved source of truth
  derivatives/                        generated; rebuildable (gitignored, but synced to the bucket)
writers/<slug>/                       writer portraits + bios (shared across songs)
works/<slug>/                         translation families — same three folders
licenses/                             full text of each song license
sources.json                          where content came from + attribution obligations
catalog.json                          generated one-file form of the whole library — the index the API reads
tools/                                zero-dependency Node scripts (build, validate, sync)
```

The content bucket holds **exactly this layout** at `s3://churchapps-content/commons/`,
derivatives included, so moving content either way is one `aws s3 sync` (see
"Sync" below). The package folder is `<slug>-<id>`: the id is the identity (parse the
**last 11 characters**; ids can begin with `-` or `_`), the slug is cosmetic, and the
folder name is frozen at creation like the id — a title edit does not rename it, because
the path is also the asset URL.

`works/<slug>/` uses the same three folders. A song that belongs to a work
inherits any file it does not override. **The score (and shared tune/art) is
shared; the words are not.** A translation always has its own
`masters/lyrics.chordpro`.

Each song package contains:

| File | Folder | What it is |
|---|---|---|
| `song.json` | `masters/` | Metadata a person asserted: id, title, writer, year, key, themes, scripture, license, per-layer rights, workRef |
| `lyrics.chordpro` | `masters/` | The words master (chords only when there is no score) |
| `score.musicxml` | `masters/` | The notes master, only once proofread (optional) |
| `score.musicxml` | `derivatives/` | Converted from `sources/tune.abc` by the normal `generate.mjs` run (four voices, all verses, no chord symbols — Open Hymnal ABC has none). Catalog confidence `converted-from-abc` until a person proofreads it into `masters/`. Any new package with an ABC source gets this automatically |
| `manifest.json` | `sources/` | One row per source file: url, date, sha256, license basis, `original` (true only when url + date are known; false = existing catalog copy, acquisition not yet backfilled) |
| `hymnary.json` | `sources/` | Harvested hymnal counts (and a churchCount snapshot) — merged at catalog build |
| `video.json` | `sources/` | YouTube performance id; a link, not an audio asset |
| `tune.mid` / `tune.abc` / `sheetPdf.pdf` / `*.ly` | `sources/` | Acquisition copies; never modified. The `.ly` files are the LilyPond sources behind Mutopia PDFs |
| `timing.json` | `derivatives/` | Word-level lyric timings. **Tracked in git** as the one exception to the derivatives rule, because only the python score pipeline can rebuild it |
| `cover.webp` | `masters/` | The package's approved cover. All current covers were generated by our tooling and are **kept, not regenerated** (decision 2026-09-07); `rights.artwork` records that. Inherited from the work if absent |
| `sources.txt` | `derivatives/` | Human-readable provenance (generated) |

`song.json` also carries `form` (section map, `status: "draft"` until a reviewer sets
`"approved"`) and `rights.text.review` on PD songs published after 1930, whose PD
claim rests on a source's dedication and needs a person to look.

The slug half of a folder name is a cosmetic title slug (native script for
non-Latin languages); a song's identity is the `id` in its `song.json` and at
the end of its folder name — deterministic, frozen at creation, and stable even
if the title is edited. `validate` errors if the two disagree. There is no
per-song versioning: git history is the record of `masters/`, and a
correction's change note is its commit message.

Git holds `sources/` and `masters/` (text, ABC, MIDI, LilyPond, approved cover) plus
`derivatives/timing.json`. Everything else in `derivatives/` is gitignored and
rebuilt with `node tools/generate.mjs` (charts, PDFs, slides, thumbs, attribution).
Until a MusicXML score exists, `chart.chordpro` is a byte copy of the lyrics master;
the score-driven chart generator replaces that step.

### Works — translation families

Translations of the same hymn are separate songs grouped by a **work**:
`works/<slug>/masters/work.json` is `{ slug, title, canonicalSongId }` where
`canonicalSongId` is the original-language song. Members carry
`"workRef": "<slug>"` in `song.json` (never a `parent` field — the parent link
in the catalog is derived from the work). Shared `tune.mid` / `tune.abc` live
in the work's `sources/`; shared `cover.webp` in its `masters/`. A member
with its own copy of a file overrides it, and `timing.json` is always per-song.
`validate` errors if a member's file is byte-identical to the work's — delete
the member copy to inherit.

**When a song gains its first translation**: give the new song
`"parent": { "id": "<original id>", "title": "..." }` and run
`node tools/migrate-works.mjs` — it creates the work (or adopts the newcomer
into an existing one), moves shared assets, and rewrites `workRef`.

## Tools

Plain Node ≥ 18, no npm dependencies. Python 3 on PATH is needed for the score step
(`generate.mjs` warns and skips it otherwise); the converter itself is vendored at
`tools/vendor/abc2xml.py`.

```
node tools/validate.mjs           # schema/consistency checks — run before committing
node tools/generate.mjs [folder]  # rebuild derivatives/ for one package or the whole library (includes the score step)
node tools/generate-scores.mjs [folder]  # the score step alone: derivatives/score.musicxml from sources/tune.abc
node tools/build-catalog.mjs      # regenerate catalog.json from the folders
node tools/find-duplicates.mjs    # report songs published twice under variant titles (--apply links them)
node tools/sync.mjs pull|push [--delete] [--dry]   # bucket ⇄ checkout, plain aws s3 sync of the whole layout
node tools/rename-packages.mjs    # one-shot rename of song folders to <slug>-<id> (reruns are no-ops)
node tools/migrate-packages.mjs   # one-shot split into sources/masters/derivatives (reruns are no-ops)
node tools/align-packages.mjs     # hymnary.json, cover.webp, form map drafts, artwork rows, PD review flags (reruns are no-ops)
node tools/harvest/import-mutopia-ly.mjs   # backfill LilyPond sources for the Mutopia PDFs (reruns skip unchanged)
```

`catalog.json` is committed and must always match a fresh build. It is what the
WorshipCommons API vendors (as `config/catalog.json`) to seed its database;
its url columns are repo-relative paths (= bucket keys).

## Sync: the content bucket is this repo, derivatives included

`s3://churchapps-content/commons/` holds exactly this layout. The bucket is the
operational master (approved submissions land there first); this repo is its
snapshot and disaster-recovery source. `derivatives/` travels in both directions
even though git ignores it, so a fresh pull is a complete, servable library and
a push never leaves the site without charts or scores.

`catalog.json` is the index. It is built from the packages, committed here, and
pushed to the bucket, where the API reseeds from it. Nothing reads folders to
discover songs; everything reads the index.

**Pull bucket → checkout** (periodically, and before any edit):

```
node tools/sync.mjs pull --delete
node tools/build-catalog.mjs && node tools/validate.mjs
git diff   # eyeball, then commit content + regenerated catalog.json together
```

**Push checkout → bucket** (after curated edits, or disaster recovery):

```
node tools/generate.mjs && node tools/build-catalog.mjs && node tools/validate.mjs
node tools/sync.mjs push          # add --delete only if you mean it
```

Song ids are frozen in each `song.json` and in the folder name, so
votes/sings/libraries keyed on song id survive any repopulation.

## Changing curated content

1. Edit the song package (or add a new one — leave out `id` and `validate` will
   tell you the id to stamp). Harvested facts go in `sources/`; asserted facts
   go in `masters/song.json`.
2. `node tools/generate.mjs && node tools/build-catalog.mjs && node tools/validate.mjs`
3. Commit content + regenerated `catalog.json` together.
4. `node tools/sync.mjs push` — never `--delete` in this direction unless you
   mean it.

The API reseeds from `catalog.json` in the bucket.
